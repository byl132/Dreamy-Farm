## 2. 真机复验烟雾测试计划（逐项）

### 预检 P0：扫码进入不卡 404（旧包 CDN 过期问题）

- **根因简述**：旧测试包引用的 CDN 资源已过期，真机加载时请求 404 → 卡在加载界面无法进入。
- **测试前置**：完成 §1 的清缓存；使用新二维码。
- **逐步操作**：
  1. 真机扫码 → 等待资源加载。
  2. 观察是否进入游戏主玩法场景（能看到农场、角色、HUD）。
  3. 打开浏览器/宿主的开发者网络面板（若可），或录屏观察是否有大量 `404` 请求。
- **观察点**：加载是否在合理时间（建议 ≤ 30s，弱网 ≤ 60s）内完成；是否出现持续 404 或转圈卡死。
- **PASS / FAIL 判据**：
  - **PASS**：新二维码可完整加载并进入主玩法场景，无持续性 404 / 卡死。
  - **FAIL**：仍卡加载或出现 404 → **阻塞**，回 BUILD-QR 重新构建（说明 CDN 资源未随新包刷新）。

### ① 移动端室内出门（靠门点出不来）

- **根因简述（已读源码确认）**：修复前 `HandleWorldClick` 在 `IsInsideRoom()` 时直接 `return`，移动端点击室内世界零响应；唯一出口是右上角 HUD「🚪 离开」按钮。修复后（Fix ①）移动端点击已镜像桌面路径，路由到 `InteriorManager.CheckFurniture() + InteriorFurniture.InteractFurniture()`：站在门口 → 弹「是否离开房间？」确认气泡 → 确认后 `ExitRoom()`；右上角「🚪 离开」按钮仍保留为兜底。
- **测试前置**：预检通过；已进入游戏；能走进任意一栋可进入建筑（主屋 / 仓库 / 商店等）。
- **逐步操作**：
  1. 走到一栋建筑的门口，点击进入室内（确认成功进入、相机正常）。
  2. **在门口附近**（靠近门的位置）**点按屏幕空白/地面**（模拟复现原 bug 的「靠门点」操作）。
  3. 观察是否弹出「🚪 是否离开房间？」确认气泡。
  4. 点击确认 → 确认回到农场室外。
  5. **兜底校验**：在室内任意位置，点击右上角「🚪 离开」按钮 → 确认也能回到室外。
  6. 重复 1–4 于至少 2 栋不同建筑（含主屋），确认非偶发。
- **观察点**：移动端「靠门点屏幕」是否能唤起离开确认；确认后是否真正回到室外；兜底按钮是否始终可用。
- **PASS / FAIL 判据**：
  - **PASS**：移动端在室内门口点按能弹离开确认并成功出房；兜底「🚪 离开」按钮始终有效；多栋建筑一致。
  - **FAIL**：门口点按仍无反应（只能靠兜底按钮）/ 确认后未出房 / 卡在室内状态 → 回 engineering-lead。

> 注意：本项验证的是「移动端点室内世界能触发离开流程」。若点击家具仍应交互（如书架/床），属正常，不属于本项失败。

### ② 河岸钓鱼（无法钓鱼 · 含调试 HUD 用法与回退方案）

- **根因简述（已读源码确认）**：移动端钓鱼管道本身正确——**湖泊区本就能钓，只有河流区不行**。根因是 `RIVER_FISH_CENTER = (-62, 0, -20)` 配合旧半径 `8`（生效半径 `8+4=12`）在 3D 世界里没覆盖玩家实际站立的河岸位置 → `IsNearPond()` 的 river 分支返回 `false` → `nearPond=false` → 移动端 `HandleWorldClick` 不进钓鱼分支 → 无钓鱼 UI。修复将 `RIVER_FISH_RADIUS` 由 `8` 放宽到 `20`（生效半径 `20+4=24`），并加入临时调试 HUD 供真机校准。
- **调试 HUD 字段说明（关键，详见附录 A）**：左上角黄字 `[DBG] pos(x.x,z.z) lake=<bool> river=<bool>`
  - `pos` = 玩家世界坐标 `(x, z)`；
  - `lake` = 是否在**湖泊**钓鱼区（中心 `(50,0,-25)`、生效半径 `16`）；
  - `river` = 是否在**河岸**钓鱼区（中心 `(-62,0,-20)`、生效半径 `24`）。
  - **对 ② 的意义**：`river=true` 即 `IsNearPond()` 的 river 分支为真 → 移动端 `HandleWorldClick` 会进入 `nearPond` 分支 → 钓鱼 UI 可触发。本项以 `river` 字段为**客观判定依据**。

- **测试前置**：预检通过；钓鱼功能已解锁（或测试账号已解锁 `fishing`）；进入游戏并能在左上角看到调试 HUD。
- **逐步操作（如何用调试 HUD 坐标判定河岸钓点是否真正可达）**：
  1. 前往**森林溪流 / 河岸**区域（不是湖泊）。边走边看左上角 HUD 的 `pos(x,z)` 与 `river=`。
  2. 走到**你（作为玩家）期望站立钓鱼的河岸点**（贴着水边的可站立位置）。
  3. **读取 HUD**：
     - 若此处 `river=true` → 继续步骤 4（预期可达）。
     - 若此处 `river=false` → 记录该 `pos(x,z)`，**直接判定 ② FAIL，启动下方回退方案**（见 §2.② 回退）。
  4. 在 `river=true` 的点，**点按屏幕**（移动端替代交互气泡）或等待钓鱼气泡出现后点击 → 确认弹出钓鱼 UI（浮漂/鱼线/开始钓鱼）。
  5. 完成一次完整钓鱼（抛竿 → 等待 → 收线）→ 确认能钓上鱼、鱼数 `+1`（`game.fishCaught`）。
  6. **对照验证（可选但推荐）**：走到湖泊区，确认 `lake=true` 且能钓（证明湖泊区未被回归破坏）。
- **观察点**：
  - 目标河岸站立点的 HUD `river` 是否为 `true`；
  - 点按是否唤起钓鱼 UI；能否完整钓上鱼；
  - 是否误触发（站在远离河流处却弹钓鱼 UI）。
- **PASS / FAIL 判据（主判据）**：
  - **PASS**：在目标河岸站立点 HUD `river=true`，且点按能开钓鱼 UI、可完成一次钓鱼；湖泊区 `lake=true` 仍能钓（无回归）。
  - **FAIL**：目标河岸点 `river=false`（调不出 UI）→ 启动回退；或 `river=true` 但 UI 崩溃/点不动（疑似 `ctx.PlaySfx` 崩溃回归）→ 回 engineering-lead。

#### ② 回退方案（仍不触发时：据调试坐标微调 `RIVER_FISH_CENTER` 再收紧半径）

> 本方案是**测量与判定流程**，具体数值回填由 engineering-lead 在主理人授权下改 `FarmConfig.lua`。QA 只负责在真机测量坐标并给出阈值。

**测量步骤（真机）**：
1. 沿玩家**实际可站立的整条河岸**走一遍，用左上角 HUD 记录每个意图钓鱼点的 `pos(x,z)`（建议 ≥ 3 个点，覆盖河岸上下两端）。
2. 计算这些点的**几何中心** `C_new = (mean_x, mean_z)`，以及离中心**最远的钓鱼点距离** `d_max`。
3. 记录中心点附近是否有「非河岸但玩家会经过」的位置（用于误触发护栏）。

**回填建议（交 engineering-lead）**：
- `RIVER_FISH_CENTER = C_new`（落在玩家真实河岸站立点几何中心附近，而非旧值 `(-62,-20)` 若它偏离实际河岸）。
- `RIVER_FISH_RADIUS = ceil(d_max) - 4`（使生效半径 `R+4` 恰覆盖 `d_max`；若需容错再 `+2`）。

**判定阈值（回退后重包复验必须满足）**：
1. **成功判据**：`river=true` 必须在**每一个目标河岸站立点**成立（即生效半径 `RIVER_FISH_RADIUS+4 ≥ 该点到中心的距离`）。
2. **误触发护栏**：生效半径 `RIVER_FISH_RADIUS + 4 ≤ 30`（即 `RIVER_FISH_RADIUS ≤ 26`）。超过 30 意味着玩家远离河流时也会误弹钓鱼 UI（体验与性能双输），视为过度放宽、需再收紧。
3. **与湖泊区不重叠**：两中心相距约 112 单位，当前量级不会重叠，无需额外约束；若最终半径极小仍可忽略。
4. **决策小结**：② 首轮复验在目标河岸点 `river=false` → 判 FAIL、启动回退测量；回退后重包复验须满足「成功判据」且「误触发护栏」。

> 调试 HUD 为临时件（`-- 发布前移除`）。**本次验证包必须保留 HUD 以便读坐标**；仅在最终发布包由 engineering-lead 移除。

### ③ `WrongDocumentError: pointer lock`（已知无害 · 记录项）

- **根因简述**：`ShouldAvoidPointerLock()`（CameraController.lua）已硬编码 `return true`，Lua 侧永不请求 pointer lock。报错来自引擎宿主（UrhoX WebGL 在 iframe 请求 pointer lock 被拒），属宿主行为，游戏规则已规避，大概率无法从游戏代码根除。
- **测试前置**：预检通过；进入游戏并操作一段时间（移动、开关面板、进出建筑/钓鱼）。
- **逐步操作**：
  1. 进入游戏，正常游玩 3–5 分钟（覆盖移动、交互、开关 UI、视角切换）。
  2. 通过宿主/浏览器日志或录屏，观察是否出现 `WrongDocumentError` / `pointer lock` 相关报错。
  3. 记录报错出现的时机（如仅在首次加载 / 每次点击 / 进出场景时）。
- **观察点**：报错是否出现；出现时游戏是否仍可正常操作（输入、点击、相机是否失效）。
- **PASS / FAIL 判据（记录项，非硬阻塞）**：
  - **PASS（可接受）**：报错仍可能出现，但**不导致崩溃 / 卡死 / 输入失效**，游戏全程可玩 → 记为「已知无害，记录即可」。
  - **FAIL（需升级）**：报错伴随崩溃、卡死、输入无响应或钓鱼/出门等功能失效 → 升级为阻塞，回 engineering-lead 查引擎/项目开关（`.project/settings.json` 等）。

### ④ 游戏卡顿（性能 · 观察项）

- **根因简述**：8/3 大量材质升 PBR 更吃 GPU，叠加每帧 `CheckProximity` 开销；轻量优化由 engineering-lead 在 ENG-READY 任务处理。QA 仅确认新包是否缓解。
- **测试前置**：预检通过；记录机型/系统版本（用于横向对照）。
- **逐步操作**：
  1. 在农场主场景行走 / 跑动 1–2 分钟，观察是否掉帧、卡顿、画面撕裂。
  2. 连续开关背包 / 商店 / 钓鱼 UI / 进出建筑，观察瞬时卡顿。
  3. 若设备/宿主有 FPS 浮窗或性能面板，开启并记录典型帧率与最低帧率。
  4. 主观评分：与历史反馈（旧包）相比，是否「明显更顺 / 持平 / 仍卡」。
- **观察点**：平均流畅度、开关 UI 的瞬时卡顿、最低帧率；是否较旧包缓解。
- **PASS / FAIL 判据（观察项，非硬阻塞）**：
  - **PASS（可接受）**：新包在目标机型上无明显卡死/长时间掉帧，较旧包有缓解或持平 → 记「观察通过」。
  - **关注（不阻塞）**：仍明显卡顿但功能可用 → 记为「待 ENG 继续优化」，进入 Phase 6 跟进，不阻断本次放行。
  - **FAIL（阻塞）**：卡顿导致无法正常操作 / 频繁无响应 → 升级，回 engineering-lead。

## 5. 质量门判定与签字（advisory）

| 维度 | 判定 |
|---|---|
| 预检 | ☐ PASS ☐ FAIL（阻塞） |
| ① 出门 | ☐ PASS ☐ FAIL |
| ② 河岸钓鱼 | ☐ PASS ☐ FAIL（若 FAIL 已启动回退测量） |

| ④ 卡顿 | ☐ 观察通过 ☐ 待 ENG 跟进 ☐ 升级阻塞 |

**质量门结论（advisory）**：
- 预检 + ① + ② 全 PASS，且 ③/④ 无升级阻塞 → **建议放行 Phase 5 → 6**。

## 附录 A：调试 HUD 字段说明

- **文本格式**：`[DBG] pos(x.x,z.z) lake=<true/false> river=<true/false>`
- **位置/样式**：屏幕左上角（`top=8, left=8`），黄色粗体，字号 11，最多 3 行（`main.lua` `id="debugFishingHud"`）。

  - `pos` = 玩家角色世界坐标 `(x, z)`（用于 ② 回退测量真实河岸点）。

## 附录 C：坐标判定公式

- `Distance2D((px,pz), C) = sqrt((px - C.x)^2 + (pz - C.z)^2)`
- `IsNearFishingZone(center, radius, x, z, extraRadius=4)` 触发条件：`Distance2D < radius + extraRadius`
- 因此：`river=true` ⟺ `Distance2D((px,pz), (-62, -20)) < 24`（当前生效半径 `20+4`）
- **生效半径通用式**：`reach = RIVER_FISH_RADIUS + 4`；回退收紧护栏 `reach ≤ 30`（即 `RIVER_FISH_RADIUS ≤ 26`）。
